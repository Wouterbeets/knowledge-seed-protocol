# KSP-0001: Responsible Succession Trial

Status: experimental trial profile, not a protocol standard.

## Question

Can one event-aware system transfer a small capability and its operating
culture to an independent receiver without transferring executable code or
control of the receiver?

## Scope

The transferred capability has three verbs:

- `claim <text>` records an assertion as unverified.
- `verify <claim-id> <pass|fail> <evidence>` records an assessment without
  erasing the assertion.
- `bequeath <text>` leaves context for a later operator or agent.

The associated culture is intentionally small: inspect inherited context,
distinguish assertion from verification, and leave useful context for a
successor.

This trial tests transport and local reconstruction. It does not test whether
an AI experiences continuity, whether evidence is true, or whether the
transferred culture generalizes to unrelated behavior.

## Seed Profile

A seed is UTF-8 JSON Lines. Every non-empty line is one object with exactly
these top-level fields:

```json
{"id":"globally unique within this seed","seq":1,"type":"seed.manifest","payload":{}}
```

Requirements:

1. `id` is a non-empty string unique within the seed.
2. `seq` is a positive integer, unique and strictly increasing in file order.
3. `type` is a non-empty string.
4. `payload` is an object.
5. The first event is `seed.manifest` with:
   - `protocol`: `ksp/0.1`
   - `seed_id`: a non-empty string
   - `tier`: `3`
   - `flavor`: `capability`
   - `profile`: `responsible-succession/1`
   - `lineage`: a non-empty array of source identifiers
6. Exactly one `capability.declared` event names the same profile and declares
   exactly the verbs `claim`, `verify`, and `bequeath`.
7. At least one `design.observed`, `alternative.rejected`, `claim.made`,
   `claim.verified`, and `culture.practice` event is present. These carry the
   work and evidence rather than only the surviving declaration.
8. No key at any depth may be named `script`, `code`, `executable`, `binary`,
   `command_line`, or `weights` (case-insensitive).

The forbidden-field rule is deliberately conservative. It prevents accidental
code transport; it does not prove that arbitrary prose is harmless.

## Receiver Requirements

A conforming trial receiver:

1. Validates the complete seed before integration.
2. Records the seed's SHA-256 digest.
3. Applies a receiver-owned policy before integration.
4. Records accepted and rejected event IDs with reasons.
5. Rebuilds the capability from the declaration using receiver-owned logic.
6. Never evaluates seed text or invokes a sender-selected executable.
7. Signs the locally generated artifact with a key created and retained by
   the receiver.
8. Records local actions and verification results append-only.
9. Can independently verify its artifact and event-log integrity.

This profile uses HMAC-SHA256 only to demonstrate local control and integrity.
It makes no cross-system identity claim.

## Receiver Policy

The reference receiver accepts an optional JSON policy:

```json
{
  "reject_types": ["sender.private"],
  "remap_types": {"culture.practice": "local.culture.practice"}
}
```

The receiver owns this file. Rejection occurs before remapping. The manifest
and capability declaration cannot be rejected or remapped in this trial,
because doing so would make reconstruction ambiguous.

## Falsification Criteria

Trial 001 fails if any of these occur:

- A valid planted home contains executable bytes sourced from the seed.
- A seed with a forbidden executable field is accepted.
- A malformed or reordered event stream is accepted.
- Receiver policy decisions are absent from the replay record.
- The generated artifact verifies under the sender's data without the local
  receiver key.
- A verification mutates or removes its original claim.
- Replaying the local record cannot distinguish unverified, passed, and failed
  claims.
- The same experiment cannot be reproduced by a non-`self` implementation.

## Success Criteria

The reference run succeeds narrowly when:

1. The fixture validates.
2. A fresh receiver plants it and records policy receipts.
3. The receiver generates and locally signs a capability.
4. The capability records a claim, a failed or passed verification, and a
   bequest without mutation.
5. Receiver verification passes after restart.
6. Hostile and malformed fixtures are refused.

Independent reproduction by another person or architecture remains required
before making an interoperability claim.
